01 · Start with ownership

Three accounts, one control chain

An external owner, such as an Ethereum or Solana user, controls a Universal Executor Account (UEA) on Push. That account owns the AGW. When the AGW acts on another chain, its Chain Executor Account (CEA) performs the destination call. A native Push owner uses its EOA directly.

The agent has its own identity

A native Push agent is an EOA. An agent with a key on another chain is represented by that key’s UEA on Push. Each rule names this Push address as its agent.

The destination account belongs to the AGW

The gateway sees the AGW as its caller and derives the AGW’s CEA. Keeping this identity intact is how the wallet holds the resulting destination position.

The same EVM key initialized against two different origin chains produces two different UEAs. Grant the rule to the UEA for the chain the agent will actually use.

03 · Keep the balances straight

The agent and the wallet pay for different things

Signer’s PC balance

Pays for the transaction that invokes the AGW on Push. An external agent uses its UEA’s PC balance.

For an external agent’s first action, deployment and funding of an undeployed UEA can use an origin-chain fee lock. Later actions require PC in that deployed UEA, as specified by agentic-mode gas checks.

AGW’s assets and PC balance

PRC20 tokens are the wallet’s working funds. Its PC covers wallet-originated outbound fees and any applicable native value sent by the wallet.

PC in the AGW does not pay the separate transaction gas of the agent’s EOA or UEA. Rules cap PC per action, not over the rule lifetime. Repeated zero-amount actions can consume the funded PC balance without consuming token spend.

  1. Owner funds the AGW

    For an external owner, assets can enter Push through the existing gateway and UEA flow before being transferred to the wallet.

  2. Owner establishes gateway allowance

    The gateway pulls PRC20 from the AGW. An owner-authorized approval is needed before positive-amount outbound execution; the agent’s universal rule does not authorize Push-side approvals.

  3. Agent invokes the wallet

    The agent’s Push identity pays invocation gas. URP checks the requested action against the selected rule.

  4. AGW sends outbound

    For a cross-chain action, the AGW calls the gateway with its assets and PC. The destination CEA belongs to the AGW.

  5. Destination CEA performs the work

    A protocol call executes from the CEA. Beneficiary checks constrain configured calldata arguments; they do not prove the protocol’s resulting outputs or asset movement.

A rule says what is allowed

Each rule names an agent, a destination and an expiry. Native rules constrain a target and selector; universal rules define an asset list with per-token caps, a per-outbound PC ceiling (maxGasPerCall) and allowed destination calls.

The target SDK rejects duplicate rules for an agent and chain; the contract itself can grant multiple active rules for the same pair. Lookup must handle that ambiguity explicitly. Rules for Push omit chainNamespace; external rules supply it.

Changing a rule creates a new rule

rules.update asserts the old spend, revokes the old rule and grants its replacement atomically. The new rule receives a new ID and fresh counters. A successful owner replacement batch adds five checkpoints. Evaluators compare snapshot counts, not only block numbers.

Revocation stops future authorization on Push. An outbound already dispatched may still complete on its destination.

Approval safety: a universal rule that allows destination approve(address,uint256) without a spender constraint can expose existing CEA balances. The newer marketplace rejects this configuration; use an agreed owner-controlled approval flow. The headline Notion example needs correction.
A destination failure does not currently have a guaranteed spend-credit path in the reviewed contract documents. Treat refunding funds, restoring spending allowance and paying gas as separate outcomes. See G07 in the gap register.
05 · Use the two SDK surfaces

Manage a wallet, or act through it

These examples show the planned API. Application signers, chain constants, rule definitions, token values and transaction calldata must be supplied by the application.

Manage as the owner

const owner = await PushChain.initialize(
  ownerSigner, { network }
);

const { wallet, rulesIds } =
  await owner.agentic.create('lending', {
    rules: [ruleOnSepolia],
  });

// Fund tokens and PC separately with normal account tooling.
// Establish required owner gateway allowances separately.
const w = owner.agentic.wallet(wallet);
const info = await w.info();
const { rules } = await w.rules.list();

Send as the agent

const agent = await PushChain.initialize(
  agentSigner,
  { network, agenticWallet: wallet }
);

const tx = await agent.universal.sendTransaction({
  to: { address: pool, chain: CHAIN.ETHEREUM_SEPOLIA },
  data: supplyData,
});

const receipt = await tx.wait();
// SDK from: AGW
// SDK origin: agent's origin account
To execute as the owner, initialize with ownerSigner and the same agenticWallet option. The signer determines the execution path. The wallet handle itself is for management.

Agentic mode rejects any transaction from. The spec also disables payGasWith, migrateCEA, rescueFunds, prepareTransaction and executeTransactions in this mode.

06 · Where the other pieces fit

An AGW can work alone or participate in a job

The broader design adds discovery, escrow and evaluation around the wallet. These are separate namespaces and WIP components.

01 · client.market

Choose a card

A card describes the agent’s service, required access, fee and promised outcome. Compilation produces wallet rules and evaluation criteria.

02 · client.agentic

Authorize work

The owner creates or selects a wallet, funds it and grants rules. The agent executes within those rules.

03 · client.job

Bind and fund

The AGW is the job client. The job hook binds rules to a provider; the job kernel holds the fee in escrow.

04 · client.evaluation

Verify and settle

START reads establish a baseline. After work is submitted, END reads and criteria determine completion or rejection.

The intended lifecycle is select card → create and fund wallet/job → record baseline → agent works → submit → evaluate → settle. A passing evaluation pays the provider; rejection returns the fee to the client. Expiry provides a refund path under the job kernel’s conditions.

The design gives checkpoints a settlement consequence: an owner-side change after the baseline can cause the provider to be paid without END reads. Label changes are cosmetic and are excluded. The hook and evaluator implementation must match this rule. Checkpoints observe owner calls, not every balance change: pulling a pre-existing allowance can change balances without a new checkpoint.
07 · Before implementation

Follow the SDK spec and make the dependencies explicit

The target API is agreed. The contract and SDK gap register records the work needed to connect it to a compatible deployment.

  • Contract entry and encoding: sender-gated execution, rule IDs, envelope encoding and compatible gateway versions need matched artifacts.
  • Atomicity: rule replacement must not inherit a non-atomic native fallback.
  • Shared definitions: rule expiry, job bindings and card identity need consistent definitions across SDK and contracts.
  • Compatibility: existing clients, Web2 reads, gas checks and transaction tracking need regression coverage.
